## 三、Superset 仪表板

### 3.1 数据源（两个，故意跨源）

| 数据源 | 连接串 | 账号权限 | 用途 |
|---|---|---|---|
| Hive 数仓（ydsh_ads） | `hive://hive@hive-server:10000/ydsh_ads` | 教学环境无认证 | 分析主数据源 |
| MySQL 业务库（ydsh_mysql） | `mysql+pymysql://ydsh_ro:***@mysql:3306/ydsh_mysql` | **只读（仅 SELECT）** | 跨源能力演示 + KPI 快照对账 |

MySQL 这份是 `export_to_mysql.py` 落的 3 张小表（1 + 12 + 48 行）快照。之所以做这份：任务书要求"同时连接 MySQL"，而原 MySQL 里只有元数据表，没有业务数据。**口径仍以 Hive 为准，MySQL 只承担"业务库"角色。**

### 3.2 数据集（8 个）

7 个物理数据集（`ads_kpi_overview`、`ads_kpi_month`、`ads_sales_daily`、`ads_category_rank`、`ads_province_sales`、`ads_pay_type_month`、`ads_store_rank`）+ 1 个虚拟数据集。

虚拟数据集 `v_province_map` 是为了解决**地图省名不匹配**：

- 我们数据里的省名是 `陕西省`、`广东省`（带"省"的全称）；
- Superset 内置中国地图的 `NAME_1` 是拼音 `Shaanxi`、`Guangdong`。

所以虚拟数据集里用 `case when` 做映射，输出 `province_map` 供地图图表使用：

```sql
case province
  when '陕西省' then 'Shaanxi'   when '重庆市' then 'Chongqing'
  when '辽宁省' then 'Liaoning'  when '河南省' then 'Henan'
  ...
  else province end as province_map
```

> 为什么不直接在 ADS 表里加英文列：英文名是"给某个 BI 工具看的展示字段"，不是业务属性。放进数仓会污染口径层，放在 BI 的虚拟数据集里更合适。

### 3.3 六个图表（任务书要求 5 个，我们做了 6 个）

| # | 图表 | 类型 | 数据集 | 关键配置 |
|---|---|---|---|---|
| ① | 全年 GMV（指标卡） | Big Number | ads_kpi_overview | metric = SUM(gmv) |
| ② | 月度销售趋势 | 折线（双系列） | ads_kpi_month | x = stat_month，GMV + 有效 GMV |
| ③ | 品类销售额 | 柱状 | ads_category_rank | x = category，SUM(sales_amt) 降序 |
| ④ | 省份销售分布 | 地图（Country Map） | v_province_map | `select_country=china`、`country_fieldtype=NAME_1` |
| ⑤ | 支付方式占比 | 饼图（环形） | ads_pay_type_month | group by pay_name，SUM(gmv) |
| ⑥ | 门店 GMV TopN | 排行表 | ads_store_rank | group by **store_id + store_name**，Top 10 |

**⑥ 的分组键很关键**：数据里 60 个门店编号只有 52 个名称（8 组同名不同店）。一开始按 `store_name` 分组，等于把两家不同门店合并成一条，GMV 虚高。改成 `store_id + store_name` 后才是真实门店排名。

### 3.4 筛选器与联动

三个原生筛选器（Native Filter），都做了实际作用域配置：

| 筛选器 | 字段 | 作用的数据集 |
|---|---|---|
| 月份 | `stat_month` | ads_kpi_month / ads_category_rank / v_province_map / ads_pay_type_month / ads_store_rank |
| 品类 | `category` | ads_category_rank |
| 支付方式 | `pay_name` | ads_pay_type_month |

同时打开交叉筛选（`cross_filters_enabled = true`）并给 6 个图表都配上 `crossFilters` 作用域，因此**点击某个品类柱子，其他图表会跟着过滤**。

生效验证：仪表板加载时筛选器已列出真实取值——**月份 12 项、品类 8 项、支付方式 4 项**（说明筛选器确实连上了数据集，不是空壳）。

### 3.5 自动化：为什么用 API 建而不是手点

任务书要求"现场演示一键部署启动全过程"。手动建 8 个数据集 + 6 个图表 + 1 个仪表板 + 3 个筛选器，熟练也要 20 分钟且不可复现。

所以 `第4周/docker/superset/bootstrap.py` 用 REST API 全自动建好，作为 `superset-init` 一次性服务在 `docker compose up -d` 时自动执行。过程中解决的四个 API 坑（都已写进代码注释）：

| 坑 | 现象 | 处理 |
|---|---|---|
| CSRF | POST 报 `The CSRF token is missing` | GET 请求 JWT 够用，写操作必须带 `X-CSRFToken` |
| `/me` 401 | 同一 JWT 访问 `/api/v1/database/` 却是 200 | 该接口自身行为，改为不依赖 owners 字段 |
| 缺 `query_context` | 取数报 `Chart has no query context saved` | 建图表时一并写入查询快照 |
| 图表未关联 | 6 个位置都显示"没有找到相关图表的组件" | API 不接受 `slices` 字段，改用模型层写 `dashboard_slices` |

### 4.3 自适应方案：为什么选 scale 而不是 rem/vw

任务书给了三个选项（rem / vw / scale），我们选 **scale**，理由：

- 大屏里 7 个面板的宽高关系是设计师定死的（4:5:3 比例），用 rem/vw 需要为每个断点重算一遍；
- ECharts 的 canvas 尺寸依赖容器像素值，rem 方案下容器尺寸随根字号变化，容易出现"图例被裁""轴标签重叠"；
- scale 方案只有一条公式，且**布局绝对不错位**：

```javascript
function fitStage() {
  const scale = Math.min(window.innerWidth / 1920, window.innerHeight / 1080);
  const left = (window.innerWidth - 1920 * scale) / 2;
  const top  = (window.innerHeight - 1080 * scale) / 2;
  stage.style.transform = `translate(${left}px, ${top}px) scale(${scale})`;
  Object.values(charts).forEach(c => c && c.resize());
}
```

配套细节：ECharts 初始化时 `devicePixelRatio: 2`，放大后不发虚；`resize` 做 120ms 防抖；再加 `ResizeObserver` 覆盖"投影切换分辨率"这种情况。

代价（如实说明）：超宽屏（21:9）两侧会留黑边。我们用径向渐变背景削弱观感，没有为此改布局——因为实训演示用的是 16:9 投影。

### 5.3 一个真实的 Prompt 缺陷与修复

初版提示词里有一条示例把"占比"写死成分母常数 `36116687.06`（全年 GMV）。结果模型照抄，问"2024 年 12 月各支付方式占比"时算出微信 **2.43%**——分母用全年、分子用单月，四个数加起来才 9.4%。

修复两处：

1. 示例改成用窗口函数：`sum(gmv) / sum(sum(gmv)) over ()`，分母跟着 WHERE 走；
2. 增加硬性约束："占比类问题的分母必须与问题限定的时间范围一致，问某月必须在该月内分组计算，绝对不要套用示例里写死的全年合计。"

修复后同一问题输出 28.15% / 25.92% / 23.11% / 22.82%，**合计 100%**。

## 七、三个"看起来能用但不能用"的结论（如实说明）

这三条和论文里的"负结果"一样重要，答辩时如果被追问"这个图能说明什么"，答案在这里。

### 7.1 时段热力图有梯度，但那是随机噪声

热力图配色一出来就有深浅，容易被解读成"午间高峰""夜间低谷"。我们做了两个检验：

- **卡方检验**：χ² = 62.74（df = 23，α=0.05 临界值 35.17）→ 统计上"不服从均匀分布"；
- 但**效应量极小**：每小时订单量 1,150~1,404 单，极差仅 19.75%；
- **跨品类一致性检验**：8 个品类的峰值时段分别是 0、4、14、18、19 点，互不一致——真实作息规律应该让所有品类都在同一时段见顶。

结论：`order_hour` 是模拟数据里随机填充的字段，深浅梯度只是大样本下的随机波动，**不能支撑任何"时段偏好"的业务结论**。热力图在本项目里证明的是"技术链路跑通 + 图表类型正确"，不是"业务洞察"。

### 7.2 门店 TopN 差点算错

见 3.3 的说明：`store_name` 不唯一（60 个编号 / 52 个名称）。若按名称聚合，TopN 第一名会是两家门店合并后的数字（1,321,107.24 元），比任何一家真实门店都高。现已改为 `store_id + store_name`。

### 7.3 三个口径不能混用

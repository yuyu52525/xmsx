## 一、联调方法

联调不是"打开三个网页点点看"，而是按**数据流向**逐层核对，每层给出**期望值 + 实测值 + 判定**。理由：图表能打开不代表数字对；数字对不代表四层能对上。只有逐层对上，才敢在答辩现场说"这个数可以回算"。

核对顺序（任何一步断了都能立刻定位是"哪一层的锅"）：

```
服务(9) → ODS(6 表/114,809) → DWD(6 条主链/111,037) → DWS(9 表/GMV 回算)
        → ADS(11 表/核心指标) → 副本(CH 11 表 + MySQL 3 表) → 应用(10 接口 + 3 端)
```

## 三、联调中发现并修复的问题（6 条）

这一节是联调的价值所在：**如果不做逐层核对，下面 6 条一条都发现不了。**

| # | 问题 | 现象 | 根因 | 修复 | 验证 |
|---|---|---|---|---|---|
| 1 | `hive-server` 反复重启 | `docker ps` 显示 `Restarting`，日志 `HiveServer2 running as process 7. Stop it first.` | 容器内 pid 文件残留（冷启动被强杀过） | `docker compose up -d --force-recreate hive-server` | 50 秒后 `healthy`，第 2～5 层核对全部可跑 |
| 2 | 容器内看不到第 5 周脚本 | `/repo/第5周` 不存在 | `docker-compose.yml` 只挂载了第 1～4 周 | 在 `hive-server` 的 `volumes` 里补 `./第5周:/repo/第5周:ro` | `docker exec hive-server ls /repo` 可见 5 个周目录 |
| 3 | 副本核对报 ClickHouse `516 Authentication failed` | `default` 用户认证失败 | `ch_client` 在 **import 时**读环境变量，脚本没先加载 `.env`，于是用 `default` + 空密码去连 | 在脚本入口 `load_dotenv(仓库根/.env)`，并 `setdefault` 补 host/port/db | 11 张表逐表行数与 Hive 相等 |
| 4 | 一次性任务被误判为失败 | `superset-init` 状态显示 `exited unhealthy`，脚本判 FAIL | 一次性任务没有健康检查，退出后 health 字段残留 | 判定逻辑改为"`-init` 结尾只看 `State.Status == exited`" | 2/2 一次性任务判 PASS |
| 5 | 服务数口径不一致 | 文档写"8 个服务"，`docker-compose.yml` 实际 9 个 | 第 4 周漏算 `mysql-init` | 统一为"9 个（7 常驻 + 2 一次性）"，同步改 `docker-compose.yml` 头部注释、`README.md`、第 4 周部署手册相关表述 | 文内 9 处全部一致 |
| 6 | 三个数字存在两套说法 | ① 清洗剔除率 3.28% / 3.29% ② 门店第一 1,321,107.24 / 708,051.42 ③ `dws_sales_week` 208 / 212 行 | ① 截断 vs 四舍五入 ② 按名称 vs 按编号 ③ 漏算 2024-W53（仅 2 天） | ① 统一 3.29%（3,772/114,809） ② 统一按 `store_id`：S029 708,051.42 元，并注明合并口径 1,321,107.24 的来源 ③ 统一 212 行，并注明 W53 只有 2 天不可当"最差周" | 三处已写入《需求文档》7.5、《数据质量清洗报告》1.2/7、《架构设计文档》4.4 |

> **修复 6 最值得记**：同一个数在两份文档里不一样，答辩时一定被问。**发现两套说法时不要选一个留下，而是查清"为什么会有两个"，然后把口径写进文档。**

## 五、复跑方式

```powershell
# 全量（含 9 个服务状态）
python 第5周/py/e2e_verify.py

# 只查数据与接口（容器状态已知时更快）
python 第5周/py/e2e_verify.py --skip-docker

# 写自定义证据文件
python 第5周/py/e2e_verify.py --out ../evidence/e2e_verify_<日期>.txt
```

也可以双击 `第5周/一键运行/1_端到端联调自检.bat`。

**判定标准**：退出码 0（全部 PASS）；退出码 2 表示有 FAIL，屏幕上会列出失败项与原因。

## 六、结论

1. **9 个服务、4 层 51 张表、2 份副本、10 个接口、3 个终端**全部连通，39 项自动核对 39 项通过。
2. 数据从 114,809 行清洗到 111,037 行，四层之间的行数变化**每一步都能解释**（剔除 3,772 = 600 重复 + 602 金额 + 1,081 数量 + 1,489 关联剔除）。
3. 核心指标**逐层可回算**：DWD 汇总 = DWS 三个粒度汇总 = 6 张订单口径 ADS 汇总 = 36,116,687.06。
4. 联调共发现 6 个问题并全部修复，其中 4 个是"文档/代码与实际不一致"（服务数、剔除率、门店口径、周数），**说明前四周的交付物确实需要一次统一口径的收口**——这正是第 5 周"整合冲刺"的意义。

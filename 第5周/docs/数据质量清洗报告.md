## 二、数据质量预评估（第 1 周，清洗的依据）

清洗不能靠"看着像脏的删掉"，先用 SQL 做全量扫描，把问题**量化成清单**，再逐类定规则。预评估按五个维度建立基线：

| 维度 | 检查方法 | 预评估结论 |
|---|---|---|
| 完整性 | `count(*) where col = '' or col is null` | 255 条缺失，集中在 3 个字段，未出现主键缺失 |
| 唯一性 | 主键 `count` vs `count(distinct)` + 整行比对 | 订单 15,600 行只有 15,000 个编号，**600 条重复** |
| 一致性 | 正则匹配标准格式（日期 / 手机号 / 时间） | 8,217 条格式不合规，全部可正则识别 |
| 准确性 | 业务阈值（年龄 1～120、金额 > 0、数量 1～50）+ 分位数分布 | 2,564 条越界，**金额分布存在断崖**（见 3.2 案例） |
| 有效性 | `select distinct 取值` 后与标准值域比对 | 60,520 条不规范，7 个字段取值种类 6～16 种 |

预评估表见 `第1周/docs/数据质量预评估表.xlsx`（含逐字段问题数、样例值、建议处理方式）。

## 三、五类脏数据的处理过程

### 3.1 完整性：缺失值

| 字段 | 缺失数 | 占该表 | 处理方式 | 依据 |
|---|---|---|---|---|
| `user.age` | 51 | 5.10% | 用有效年龄均值填充 + `age_filled = 1` | 年龄参与年龄段分组，空值会让该用户掉出所有年龄段 |
| `user.email` | 193 | 19.30% | **不填充，保留空值 + `email_missing = 1`** | 邮箱非必填，伪造会污染用户触达分析；标记后可按"有/无邮箱"分组 |
| `product.launch_date` | 11 | 1.83% | 按同品类上架日期中位数补全 + `launch_date_filled = 1` | 上架日期用于商品生命周期分析，空值无法求"在架天数" |
| `order.pay_amount` | 0 | 0% | 无需处理 | 金额字段完整，缺失问题不在这张表 |

**修复率：可修复项 62/62 = 100%；邮箱 193 条为"标记不修复"（策略性选择，不计入修复率分子）。**

### 3.2 唯一性：重复值

先判"重复"的定义，再动手删——这一步决定了后面所有指标准不准。

| 检查项 | 实测 |
|---|---|
| `ods_order` 总行数 | 15,600 |
| `order_id` 唯一数 | 15,000 |
| 整行完全重复（所有字段一致） | 400 行 |
| 同 `order_id` 但部分字段不同（**异构重复**） | 200 行 |
| 合计重复行 | **600 行** |
| `order_item.item_id` / `behavior.behavior_id` 重复 | 0 |

**异构重复的处理**：600 条里 200 条不是整行相同，而是同一订单号出现两次、金额/时间略有差异（模拟"重复推送"）。若只按"整行去重"删 400 条，会留下 200 个同号订单，导致**订单量虚高 200、GMV 虚增约 28 万**。因此按 `order_id` 分组、保留每组第一条（`row_number() over (partition by order_id order by update_time desc) = 1`），删 200 条。

**修复率：600/600 = 100%。**

### 3.3 一致性：格式不统一

| 字段 | 问题数 | 具体表现 | 统一为 |
|---|---|---|---|
| `user.register_date` | 125 | `2023/11/25` 式 100 条 + `20231125` 式 25 条 | `yyyy-MM-dd` |
| `user.phone` | 102 | `138-9212-7520` 带横线 | 11 位纯数字 |
| `order.order_date` | 1,902 | `2024/07/26` 斜杠式 | `yyyy-MM-dd` |
| `behavior.behavior_time` | 6,088 | `2024/11/05 10:20` 斜杠且缺秒 | `yyyy-MM-dd HH:mm:ss` |
| `order.order_time` | 0 | 全部规范 | — |
| `order_timestamp` | — | 原表没有该字段 | 由日期 + 时间 `concat` 生成 |

实现方式：

```sql
-- 日期：8 位数字拆段，其余斜杠换横线
case when regexp(register_date, '^[0-9]{8}$')
     then concat(substr(register_date,1,4),'-',substr(register_date,5,2),'-',substr(register_date,7,2))
     else regexp_replace(register_date, '/', '-') end

-- 手机号：先剥离非数字，再校验长度
regexp_replace(phone, '[^0-9]', '')            -- 102 条剥离后正好 11 位

-- 行为时间：斜杠换横线，缺秒补 :00
case when length(t) = 16 then concat(replace(t,'/','-'), ':00')
     else replace(t,'/','-') end
```

**修复率：8,217/8,217 = 100%。**

### 3.4 准确性：异常值

| 对象 | 判定规则 | 处理 | 条数 | 理由 |
|---|---|---|---|---|
| 订单实付 | `< 0` | **删除** | 310 | 负支付业务上不成立，且无法推断真实值 |
| 订单实付 | `> 11,356.33`（IQR 上限） | **删除** | 312 | 见下方案例一 |
| 用户年龄 | `< 1` 或 `> 120` | 均值填充 + 边界强校验 | 27 | 年龄是硬业务约束 |
| 商品售价 | `≤ 0` 或 `> 100,000` | 按**同类目中位数**修正 + `price_fixed = 1` | 36 | 维度表不能删行，否则事实表外键悬空 |
| 明细数量 | `≤ 0` 或 `> 50` | **删除** | 1,081 | 正常值只有 1～5，99 是 20 倍离群 |
| 明细单价 | `≤ 0` | 按**同商品有效单价中位数**修正 + `price_fixed = 1` | 798 条命中，实际修正 773 条 | 见下方案例二 |

#### 案例一：为什么不用手册建议的 P99 阈值

实测 `pay_amount` 分位数：**P50 = 2,542.53，P95 = 4,835.89，P99 = 5,516,776.62**。

P99 被抬到 550 万，是因为异常值占 3.8%（312/15,600）**已超过 1%**——第 99 百分位本身就落在异常堆里。按 P99 当上限，会把 291 条百万级脏数据当"正常大额订单"保留。

改用箱线图 IQR 法：

```
Q1 = 1,293.39　Q3 = 3,809.12　IQR = 2,515.74
上限 = Q3 + 3 × IQR = 11,356.33
```

再用业务事实交叉验证：正常订单 14,978 条**全部 ≤ 5,000 元**，异常订单 312 条**全部 ≥ 100,000 元**，**5,000～100,000 元之间一条数据都没有**——金额分布在 5 千到 10 万之间有明显断崖。IQR 上限正好落在断崖内，既不会误删真实大额订单，也不会漏掉异常值。

> 这条规则的意义：**阈值不能从教科书抄，要用数据自己的分布形状验证一遍。**

#### 案例二：明细单价为什么"修正"而不是"删除"

第一次跑 ETL 时发现"明细分摊合计 35,231,857.66 元，比有明细订单实付 35,833,304.41 元少了约 60 万"。逐层排查后定位到 773 条负单价：`quantity × unit_price` 为负 → 订单明细原价合计 ≤ 0 → 分摊公式的保护分支（`order_amt > 0`）直接返回 0 → 该订单的所有明细金额归零。

改为"用同商品有效单价中位数修正"后，分摊闭合误差降到 **0.65 元**（14,284 单逐行四舍五入的累计量）。

> 这是一个必须写的教训：**异常值不处理干净，下游窗口函数会静默算错，而不会报错。** 表看起来有数，数加起来不对。

**修复率：2,564/2,564 = 100%（删除 1,683 条 + 修正 881 条）。**

### 3.5 有效性：枚举取值不规范

| 字段 | 清洗前种类 | 不规范条数 | 典型脏值 | 标准值域 | 清洗后种类 |
|---|---|---|---|---|---|
| `user.gender` | 8 | 498 | 男/女/M/F/male/female/未知/空 | 男 / 女 / 未知 | **3** |
| `user.member_level` | 12 | 108 | 金卡会员/金卡/gold/钻石/silver/normal/空 | 普通/银卡/金卡/钻石会员 | **4** |
| `order.order_status` | 12 | 1,375 | 已完成/完成/3/已支付/2/待支付/1/已取消/cancelled/4/退款中 | 待支付/已支付/已完成/已取消/退款中 | **5** |
| `order.pay_type` | 7 | 651 | 支付宝/alipay/微信支付/微信/wechat/银行卡/货到付款 | 支付宝/微信支付/银行卡/货到付款 | **4** |
| `order.channel` | 6 | 310 | APP/app/PC官网/pc/小程序/门店 | 门店/APP/小程序/PC官网 | **4** |
| `behavior.behavior_type` | 10 | 57,551 | pv/PV/浏览、cart/Cart/加购、fav/收藏、buy/购买 | 浏览/加购/收藏/购买 | **4** |
| `product.category` | 16 | 27 | 8 个类目各带"尾巴空格"变体 | 8 个一级类目 | **8** |

处理要点：

1. **先 `select distinct` 全量扫描取值，再逐值写 `case when`**。不先看清单就写映射，必然漏值——本项目第一版映射漏了 `silver`，导致 12 条银卡用户掉成空值，被 `level_imputed` 误标成"普通会员"。
2. **中文标准值优先**：`male` 映射到"男"而不是反过来。下游报表、图表全是中文，让标准值贴近业务语言。
3. **空值按业务含义补**：`member_level` 空 → 普通会员 + `level_imputed = 1`（14 条）；`gender` 空 → 未知（不猜）。
4. **文本规范化**：`category` / `sub_category` / `brand` 统一 `trim` + 压缩内部空白 + `upper`，防止"运动户外 "与"运动户外"被分成两组。

**修复率：60,520/60,520 = 100%；7 个字段取值种类全部收敛（8→3、12→4、12→5、7→4、6→4、10→4、16→8）。**

## 七、第 5 周联调中对质量结论的复核（新增）

第 5 周做端到端联调时，对清洗结论做了三项复核，并修正了一处口径表述：

| 复核项 | 方法 | 结果 |
|---|---|---|

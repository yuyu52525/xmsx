【原因（如实记录，不美化）】

1. 时间压力：第 4 周的 Superset 初始化链路当天才彻底打通（前后修了 4 个问题：
   数据源 422、CSRF、仪表板图表关联、query_context），到能演示时已经接近交稿时间。
2. 判断失误：当时认为"只有我一个人提交，分支没有协作价值"，把分支理解为
   "多人协作用的"，忽略了它真正的价值是"回滚粒度"。
3. 提交粒度过粗：6f43b92 一次提交了 60+ 个文件（后端 + 前端 + docker + 文档），
   如果其中某一类要回退，几乎只能整体回退。

【影响评估】

- 对功能：无影响，第 4 周交付物可正常复现（第 5 周 39 项联调核对已复验）。
- 对历史可读性：有影响。git log --graph 在第 4 周这段是直链，看不出"做了什么模块"。
- 对评分项"Git 历史规范"：有影响，属于明确的过程留痕缺失。

【整改措施（已执行）】

1. 第 5 周起恢复"功能分支 + PR"流程：本轮工作全部在 docs/week5-integration 分支上，
   完成后再合并，PR 记录见 pull_request_16_week5_integration.txt。
2. 提交粒度按"一件事一个提交"拆分：本轮 6 个提交分别是
   docker 配置 / 联调脚本 / 五篇文档 / README / Git 记录 / 证据刷新。
3. 不回改历史：不使用 rebase / filter-repo 重写已推送的第 4 周提交。
   理由——已推送的历史被重写会让所有克隆过仓库的人对不上，代价大于收益；
   正确做法是把问题记录在此，并用后续规范证明已经纠正。
4. 建立并遵守约定式提交前缀：feat / fix / docs / chore / refactor / test + 中文范围与摘要。

【结论】

这三个提交是本项目 Git 规范上的一次明确退步。保留记录而不是抹掉，是因为
"知道为什么错"比"看起来没错"对下一个项目更有用。
